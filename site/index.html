Events & ticketing you host yourself

The wifi dies.
The gate keeps working.

Every other ticketing platform asks a server "is this ticket real?" — so when the venue's network drops, the queue stops. Cackle doesn't ask. A ticket is a signed capability the scanner can check by itself, so your door keeps admitting guests through a dead router, a dead uplink, or a dead server.

The shape of an event

Sell online. Admit offline. Reconcile later.

You need a connection to sell a ticket, and you need one afterwards to see what happened. In between — the part where four hundred people are standing in a field waiting to get in — you need nothing at all.

Step 01

Set up and sell

Create an event, add ticket types with their own prices, caps and sales windows, publish it. Buyers check out and get a QR code that is signed by this event's key — every event has its own, so a leaked key is one event's problem, never the platform's.

Needs a connection · organiser and buyers
Step 02

Pull the bundle once

Before doors, each scanning phone downloads one scan bundle: the event, its public keys, which tickets are currently valid, and who is already inside. It is a few hundred kilobytes and it is the last network call the device needs to make.

Needs a connection · once, before doors
Step 03

Run the door on nothing

Scan, verify, admit — signature check, event check, revocation check, duplicate check, all against what the phone already holds. Admissions queue on the device. When signal comes back, every gate's log uploads and merges; nothing is overwritten.

Needs nothing · the whole event

A ticket proves itself

The QR carries a payload and an Ed25519 signature over it. A scanner holding the event's public key can prove the ticket was issued by you and has not been altered — with no database, no lookup and no server in the room.

Refunds still stick, offline

A signature only proves a ticket was issued once. The bundle also carries the set of tickets currently valid, so a refunded or voided ticket is refused at a gate with no signal — and an event you cancelled admits nobody at all.

Re-pull the bundle at shift changes and that list gets fresher. It is a snapshot, and the page says so rather than implying it is live.

Nothing is lost quietly

Each device keeps an append-only log of what it decided. When gates sync, every device's verdict is stored verbatim next to the reconciled one — so a duplicate that got through is a row you can find, not a number that silently disagrees.

If a phone is dropped in a puddle, you lose that device's log. You never lose the ability to run the door.

At the door

Four answers, readable at arm's length.

Door staff have three seconds, a queue, bad light and a phone they are holding at hip height. The gate screen floods with one colour, one icon, one instruction — and the phone buzzes a different rhythm for each, because colour on its own fails exactly the people and conditions a gate has to work for.

LET THEM IN
Signature checks out, ticket is valid for this event, nobody has used it here.
one short pulse
ALREADY SCANNED
A real ticket that has been through a gate before. The screen names which one — this door, or another.
two quick taps
DO NOT LET THEM IN
Forged, altered, expired, refunded, or signed with a key this event does not know.
one long buzz
WRONG EVENT
Genuinely signed — for something else. They are at the wrong door, not holding a fake.
two long buzzes

Read this before you plan around it: double-scan is detected, not prevented.

Two gates that cannot see each other cannot agree about anything at the moment a ticket is presented. If someone walks a copied QR from the north gate to the south gate while both are offline, both gates will open. That is not a gap in this implementation — it is what "offline" means, and no amount of clever merging invents a conversation between two devices that are not talking.

What Cackle actually does is refuse to hide it. Every device's own verdict is kept verbatim, and GET /api/events/{id}/admission-conflicts lists every ticket admitted more than once and how many extra people that let in. Re-pulling a bundle mid-event narrows the window; replicating between nodes narrows it further. Neither closes it, and nothing here will ever tell you it does.

If you need a hard cap on bodies through a door, you need a door that is online, and you should buy something else — or accept the trade knowingly, which is what most festivals in most fields already do.

Getting paid

Money goes from your buyer to you.

Cackle never holds funds. There is no escrow, no platform wallet, no hold-and-release, and no cut. It creates the order, hands the payment to whichever rail you chose, and records what came back — the money moves between the buyer and your account, never through one of ours.

Always on · the default

Cash, transfer, at the door

The manual rail is enabled in every deployment and cannot be turned off. It makes no network call, needs no keys and no account: the buyer pays you however you already get paid, and you mark the order settled. This is a complete way to run an event.

  • no keys
  • no network
  • no account
Optional · fiat

Cards and local rails

Paystack ships natively, including the payout and banking calls. Around twenty more processors — Stripe, Adyen and the rest — are reached through patala, the payment substrate this suite shares, on an opt-in build.

  • paystack
  • stripe
  • adyen
  • +17 via patala
Optional · crypto

Stablecoins and Lightning

A native stablecoin watcher settles orders by watching an address you control. BTCPay and lnbits come through the same patala build. Non-custodial throughout — the keys are yours, and Cackle only ever reads confirmations.

  • stablecoin
  • btcpay
  • lnbits

No privileged country or currency

Currency is per event, defaulting from your organisation. Run events in EUR, INR and JPY at the same time and each keeps its own. Cackle was built in South Africa and used to read that way; that framing was wrong and has been taken out of the code as well as the copy.

Money is integers, always

Every amount is minor units plus an ISO-4217 code — never a float, never an assumed divide-by-100. JPY has no minor unit and KWD has three; getting that wrong overcharges a buyer 100× or sells your event out for 1% of its price, so the exponent table is real and the code fails closed on a currency it does not know.

Sandbox-test any processor before it touches real money.

None of the card or crypto processors have been run against a live merchant account or sandbox from this repository. They are ported from tested code and covered by unit tests that prove they handle the documented shapes and fail closed on a bad signature, a wrong amount or a timeout — that is not the same as proving they talk correctly to the live provider. Run one test transaction end to end before you sell anything through it. The manual rail needs no such check: it makes no call at all.

Yours to run

One binary. Your box, or your cloud.

Go compiles the database and the whole web app into a single executable. There is no Postgres to run, no Redis, no Node process, no queue worker, and nothing to sign up for. Copy the file to a machine and run it.

A box in the venue

The machine most resistant to your venue's network is the one standing in it. Run Cackle on a laptop behind the box office and gates reach it over the local network — or over nothing at all, which is the design.

A cloud node

One small VM, one volume, one process. The database file is the instance: every org, event, ticket, key and order. Back that file up and you have backed up everything.

More than one node admissions only

A venue node and a cloud node can replicate their admission ledgers to each other, so the conflict report reads the same wherever you open it and each node's gates learn sooner about admissions at the other's.

Only admission claims replicate — not events, tickets, orders or keys. It is not a backup, and it does not prevent a double admission either.

Signing keys sealed at rest

Event private keys are encrypted in the database. Without the unlock material the server refuses to start rather than falling back to plaintext — there is no fallback mode.

Your organisers get a page

Every event has a real page from the moment it is created. A host can submit their own structured page, or take the public JSON and render the event on their own site.

Open source, both licences

MIT or Apache-2.0, your choice. Releases are signed and verified by a script with a fail-closed test matrix, so a tampered artefact does not verify.

No calls home

No telemetry, no analytics, no licence check, no default connection to anything — including anything of ours. An air-gapped install is a supported install.
